# IyziTrace 1.4.0

Released 2026-11-01: platform bundle 1.4.0 and Grafana plugin 1.4.0, on the
[v1.4.0 release page](https://github.com/antreklabs/iyzitrace-releases/releases/tag/v1.4.0).
These notes cover everything since 1.2.0, including 1.3.0.

## What's new

### Downstream services

- The databases, caches, message brokers and external services your services
  call now appear as downstreams on Horizon, Atlas, Nexus, Service Map and
  Services. They are found from the calls in your traces. Each one shows its
  call rate and latency, measured from those calls, and what is inside it
  (databases, topics, queues).
- A downstream is identified one way everywhere: by its system and address.
  The same database no longer appears under different names on different
  screens.
- A downstream is *discovered* when it is only seen in traces, and turns
  *monitored* when its own metrics arrive with the same address. Hosts,
  processes, containers and Kubernetes objects show the same two states.

### Incoming Calls / All Calls

- A switch in the top bar sets what the request figures count. *Incoming
  Calls* counts only the operations a service serves: requests it receives,
  requests from callers that send no trace, work that starts on its own (such
  as scheduled jobs), and browser or mobile sessions. Throughput, errors and
  latency then describe what the service was asked to do. *All Calls* also
  counts the calls the service makes to others.
- Every screen computes these figures the same way, so a service shows the
  same number wherever you look at it.

### IyziTrace semantic conventions

- At ingestion the platform adds a small set of `iyzitrace.*` attributes to
  every span. They sit next to the OpenTelemetry attributes and never replace
  them:
  - `iyzitrace.span.type`: `http`, `database`, `cache`, `messaging`, `rpc`,
    `genai`, `internal` or `unknown`;
  - `iyzitrace.span.name`: a readable operation name, built from the
    OpenTelemetry fields when the sender gives none;
  - `iyzitrace.operation.origin`: whether the operation was called, started on
    its own, or came from a browser or mobile app;
  - `iyzitrace.span.streaming`: set on streams (WebSocket, streaming RPC), so
    their duration stays out of latency figures;
  - `iyzitrace.peer.system`, `iyzitrace.peer.instance` and
    `iyzitrace.peer.target`: the downstream's system, address, and the
    database, topic or queue inside it.
- Every screen, the inventory and the AI agent read the same meaning from
  them. You can use them in your own queries too: as span attributes in
  TraceQL, and as `iyzitrace_*` labels on the span metrics.

### Exponential histograms

- Latency is now also written as exponential (native) histograms, next to the
  classic ones. With them, percentiles are no longer snapped to fixed bucket
  boundaries, and floors such as `< 10 ms` disappear.
- Thanos runs IyziTrace's patched image, which downsamples these histograms
  correctly.
- The screens keep reading the classic form until you switch them over, at
  least 2 days after the upgrade (step 6 below).

### Faster screens and longer history

- Long ranges open much faster. On a production-sized test dataset, the
  overview screens open a 30-day range in 15–23 s instead of 32–130 s, where
  some used to fail.
- Traces, logs and raw metrics are kept for 30 days instead of 14. Downsampled
  metrics are unchanged: 90 days at 5 minutes, 1 year at 1 hour.
- Stored metrics carry fewer labels, so the metric store grows more slowly.

### AI

- Investigations are saved on the platform, not in the browser.
- Alert auto-triage, off by default (Settings → AI).
- Usage caps and policy per department, scheduled digests, and questions in
  plain language.
- MCP: connect your own MCP servers to the investigation agent, and use
  IyziTrace as an MCP server.
- Remediation plans: the agent proposes a fix plan, and the approved steps run
  through a runner you install in your own network.

### Security and operations

- Every query is confined to exactly one department, and the query paths are
  read-only.
- All images were updated. Every image and dependency was scanned before the
  release: critical and high findings were fixed or, where no fix exists yet,
  reviewed and documented.
- `iyzitrace upgrade` pulls every image before it stops anything, backs up the
  configuration and the databases, and waits until every service is healthy.
- `iyzitrace rollback` is new: it returns to the previous version from that
  backup.

## Before you upgrade

- **Plugin and platform go together.** Platform 1.4.0 needs plugin 1.4.0;
  until the plugin is upgraded, every screen says "This plugin version is no
  longer supported by your platform".
- **Your own dashboards and alerts.** Span-metric labels were renamed. Update
  every query of your own that reads one of these:

  | 1.2.0 label | 1.4.0 label |
  |---|---|
  | `span_name` | `iyzitrace_span_name` |
  | `type` | `iyzitrace_span_type` |
  | `client_operation_name` | `client_iyzitrace_span_name` |
  | `server_operation_name` | `server_iyzitrace_span_name` |
  | `client_type` | `client_iyzitrace_span_type` |
  | `server_type` | `server_iyzitrace_span_type` |

  The IyziTrace screens need no change.
- **Files you edited under `config/` are replaced** (for example Alertmanager
  receivers or `nginx.conf`). Your old copies are kept in
  `.upgrade-backups/` in the install directory. Lines you added to `.env` are
  kept.
- **Disk.** History grows to 30 days instead of 14, so plan for about twice the
  disk. The history step also needs temporary space: several GB for a busy
  department.
- **Python 3.6 or later** on the platform host, for the history step.
- **Downtime.** The platform stops for a few minutes during the upgrade.
- **Inventory clean-up.** Processes, containers, pods, operations and external
  services that stop reporting are now removed after 24 hours instead of 7
  days. To keep 7 days, add `INVENTORY_RETENTION_TRANSIENT=168h` to `/etc/iyzitrace/.env`
  after the upgrade and run
  `sudo iyzitrace up inventory-service --install-dir /etc/iyzitrace`.

## Upgrading from 1.2.0 (Docker)

Run these on the platform host. The commands use the default install
directory, `/etc/iyzitrace`. If yours is elsewhere, for example
`/opt/iyzitrace`, put your path in its place in every command.

**1. Install the 1.4.0 CLI.** The example is for Linux on x86_64. Use the file
that matches your machine from the release page, for example
`iyzitrace-1.4.0-linux-arm64` on ARM.

```bash
curl -fLO https://github.com/antreklabs/iyzitrace-releases/releases/download/v1.4.0/iyzitrace-1.4.0-linux-amd64
sudo install -m 0755 iyzitrace-1.4.0-linux-amd64 /usr/local/bin/iyzitrace
iyzitrace version
```

**2. Upgrade the platform.** Answer `y`. It ends with `upgraded 1.2.0 -> 1.4.0`.

```bash
sudo iyzitrace upgrade --install-dir /etc/iyzitrace --require-checksum --bundle-url https://github.com/antreklabs/iyzitrace-releases/releases/download/v1.4.0/iyzitrace-bundle-1.4.0.tar.gz
sudo iyzitrace status --install-dir /etc/iyzitrace
```

Add `--dry-run` to the same command first if you want to see which files
change without changing anything. If the platform does not come up healthy,
`sudo iyzitrace rollback --install-dir /etc/iyzitrace` returns to 1.2.0.

**3. Upgrade the plugin.** Right after step 2, install plugin 1.4.0
(`antreklabs-iyzitrace-app-1.4.0.zip` on the release page) the same way you
installed 1.2.0, and restart Grafana. Your saved label settings move to the new
names by themselves.

**4. If Grafana runs on another host,** tell the platform where it is. Agent
Manager and the AI settings need it to check that you are a Grafana
administrator.

```bash
echo 'GRAFANA_URL=http://10.0.0.5:3000' | sudo tee -a /etc/iyzitrace/.env
sudo iyzitrace up auth-service --install-dir /etc/iyzitrace
```

Keep both hosts' clocks in sync (NTP). If they drift more than 60 seconds
apart, these pages fail on and off with "The platform rejected this
department's API key".

**5. Bring the last 30 days of history to the new labels.** Without this,
ranges from before the upgrade show empty operation, dependency, database and
map views. Run it once for each department that sent data before the upgrade
(the ids are on the plugin's Departments page, including `__default`):

```bash
cd /etc/iyzitrace
sudo python3 scripts/history_relabel.py apply --tenant __default --tmp-dir /var/lib/iyzitrace/relabel-tmp
```

- It only adds the new labels; your data stays as it is. It takes several
  minutes per department.
- If it ends with `run apply again after <time>`, run the same command again
  after that time (at most 12 hours later). Until then, restart single
  services only (`sudo iyzitrace up <service> --install-dir /etc/iyzitrace`),
  never the whole stack.
- When every department is done, delete `/var/lib/iyzitrace/relabel-tmp`.

**6. Optional: switch the screens to exponential histograms.** Wait at least 2
days after the upgrade, so the new form has some history:

```bash
echo 'IYZITRACE_HISTOGRAM_KIND=native' | sudo tee -a /etc/iyzitrace/.env
sudo iyzitrace up auth-service --install-dir /etc/iyzitrace
```

To go back, remove the line and run the same `up` command. Nothing is lost:
both forms are always written.
